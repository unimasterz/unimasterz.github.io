PHP: Guzzle, raw cURL, and stream contexts

Three mechanisms that install nothing in common: Guzzle keeps its own option, the cURL functions take their own constants, and the built-in file functions read only a stream context you pass in by hand. A single script can route its main work correctly and send one small fetch direct, with nothing in the output to suggest it.

Three mechanisms, no shared state

You callReads
Guzzleits own proxy option, and the environment
curl_* functionsCURLOPT_PROXY, and lowercase environment variables
file_get_contents, fopenonly a stream context you pass in

A script that uses Guzzle for its main work and file_get_contents for one small fetch will route the first and send the second direct. This is the single most common PHP mistake here, and it is silent.

Guzzle

use GuzzleHttp\Client;

$c = new Client([ 'proxy' => [ 'http' => 'http://user:pass@198.51.100.14:8080', 'https' => 'http://user:pass@198.51.100.14:8080', 'no' => ['localhost', '127.0.0.1', '.internal'], ], 'timeout' => 20, 'connect_timeout' => 5, 'http_errors' => false, ]);

echo $c->get('https://api.ipify.org')->getBody(); ```

Same shape as the Python dictionary: keyed by the target's scheme, both values describe the hop, and both are http://.

The no key is an array here instead of a comma separated string, which is more pleasant and means one fewer parsing rule to remember.

A single string form also works and applies to everything:

'proxy' => 'http://user:pass@198.51.100.14:8080',

Guzzle reads the environment when no option is given. To take the environment out of the picture entirely, pass 'proxy' => ''.

Raw cURL

$ch = curl_init('https://api.ipify.org');
curl_setopt_array($ch, [
    CURLOPT_PROXY          => '198.51.100.14:8080',
    CURLOPT_PROXYUSERPWD   => 'user:pass',
    CURLOPT_PROXYTYPE      => CURLPROXY_HTTP,
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_CONNECTTIMEOUT => 5,
    CURLOPT_TIMEOUT        => 20,
    CURLOPT_NOPROXY        => 'localhost,127.0.0.1,.internal',
]);
$otvet = curl_exec($ch);
if ($otvet === false) { echo curl_error($ch); }
curl_close($ch);

CURLOPT_PROXYUSERPWD keeps credentials out of the url, so percent-encoding is not needed. Prefer it.

For the other scheme family:

CURLOPT_PROXYTYPE => CURLPROXY_SOCKS5_HOSTNAME,

That constant is the equivalent of the trailing h: the hostname goes to the far end. CURLPROXY_SOCKS5 resolves locally.

Stream context, for the built-in functions

$ctx = stream_context_create([
    'http' => [
        'proxy'           => 'tcp://198.51.100.14:8080',
        'request_fulluri' => true,
        'header'          => "Proxy-Authorization: Basic " . base64_encode("user:pass") . "\r\n",
        'timeout'         => 20,
    ],
]);
echo file_get_contents('https://api.ipify.org', false, $ctx);

Three details that catch people.

The scheme is tcp://, not http://. Any other value is ignored.

request_fulluri must be true, or the request line is sent in the wrong form and the hop returns an error.

Credentials go in a header you build yourself. There is no option for them.

A stream context does not tunnel for encrypted targets

For an https url this mechanism does not open a proper CONNECT tunnel in the way cURL does. For anything encrypted, use Guzzle or cURL. The stream context is for plain http and for the cases where you have no choice.

Finding what a library actually uses

If a third party package routes some requests and not others, find out which mechanism it calls:

grep -rn "curl_init\|file_get_contents\|fopen\|GuzzleHttp" vendor/postavshchik/

That answers in seconds a question that is otherwise guesswork.

Confirming it works

echo "guzzle: " . $c->get('https://api.ipify.org')->getBody() . "\n";
echo "streams: " . file_get_contents('https://api.ipify.org', false, $ctx) . "\n";

Check every mechanism your codebase touches, not just the main one. The mechanism you forgot is the one going direct. Comparing all three against one known address makes the odd one out obvious in a single run.
