systemd: giving a service its own settings

systemd services inherit almost nothing from your shell, the same way cron does. The difference is that systemd gives you a proper place to put the settings, and real logs when they are wrong.

sponsor

What a service actually inherits

Nothing from your login shell. Not ~/.bashrc, not ~/.profile, not what you exported five minutes ago.

systemctl show sbor.service -p Environment

That is the full list, and on a fresh unit it is usually empty.

Giving one service its own settings

[Unit]
Description=Ночной сбор каталога
After=network-online.target
Wants=network-online.target

[Service] Type=oneshot User=sbor WorkingDirectory=/opt/sbor

EnvironmentFile=/etc/sbor/hop.env Environment=LANG=en_GB.UTF-8 Environment=TZ=Europe/Berlin

ExecStart=/opt/sbor/venv/bin/python /opt/sbor/katalog.py

TimeoutStartSec=4h StandardOutput=journal StandardError=journal ```

# /etc/sbor/hop.env, права 0640, владелец sbor
http_proxy=http://user:pass@198.51.100.14:8080
https_proxy=http://user:pass@198.51.100.14:8080
HTTP_PROXY=http://user:pass@198.51.100.14:8080
HTTPS_PROXY=http://user:pass@198.51.100.14:8080
no_proxy=localhost,127.0.0.1,::1

EnvironmentFile keeps credentials out of the unit file, which usually lives in version control. The unit is public, the env file is not.

Both cases of each variable, for the reasons on the environment page.

`After=network.target` is not enough

network.target fires when the networking service has started, which is before an address has been assigned. A job that starts there may find no route. network-online.target with the matching Wants= waits for actual connectivity, and it is the difference between a job that works on reboot and one that fails once in every three.

The timeout that kills long jobs

TimeoutStartSec defaults to 90 seconds for a oneshot service. A collection job that takes four hours is killed at ninety seconds with a message that reads like a startup failure.

Set it to something above the longest run you expect, or infinity if the job bounds itself.

Timers instead of cron

# sbor.timer
[Unit]
Description=Ночной сбор, ежедневно

[Timer] OnCalendar=*-*-* 03:15:00 RandomizedDelaySec=900 Persistent=true Unit=sbor.service

[Install] WantedBy=timers.target ```

systemctl enable --now sbor.timer
systemctl list-timers sbor.timer

Three things a timer gives you that cron does not.

RandomizedDelaySec spreads the start over fifteen minutes, so the job does not begin at exactly the same second every night. That is worth having for the same reason random pauses are.

Persistent=true runs a missed job after a reboot instead of skipping it silently.

And systemctl list-timers tells you when it last ran and when it runs next, which is a question cron cannot answer at all.

Reading what happened

journalctl -u sbor.service --since "yesterday" --no-pager
journalctl -u sbor.service -p err --since "-7 days"
systemctl show sbor.service -p ExecMainStatus -p Result

The last command is the one to run first: it tells you whether the job succeeded, was killed, timed out, or never started, without reading a line of log.

Overlap

[Unit]
# oneshot-сервис не запустится повторно, пока идёт предыдущий

A oneshot service will not start a second copy while the first is running, so you get the flock behaviour for free. That alone is a reason to prefer a timer over cron for anything that might overrun.

Confirming it works

systemd-run --uid=sbor --property=EnvironmentFile=/etc/sbor/hop.env \
  --wait --pipe curl -s https://api.ipify.org

That runs one command in exactly the environment your service will get, and prints what comes back. Keep the expected answer written down next to the unit, which is easy when the service always leaves through the same fixed address. It answers in five seconds a question that would otherwise mean editing the unit and waiting for the next scheduled run.
