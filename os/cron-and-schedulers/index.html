Wirebound / Runtime and machine

cron and schedulers: the empty environment trap

The classic: works when you run it, fails every night.

sponsor

What cron actually gives you

Not your shell environment. Not your profile. Roughly this:

HOME=/home/user
LOGNAME=user
PATH=/usr/bin:/bin
SHELL=/bin/sh

That is the whole thing on most systems. No proxy variables, no language settings, no additions your profile makes to PATH, no virtualenv.

See it for yourself:

* * * * * env > /tmp/cron-env.txt

Wait a minute, read the file, remove the line. That output is the truth for your machine and it is shorter than people expect.

Why the job fails

Three failures, in order of frequency.

No proxy variables. The job goes direct. If the target only answers through the hop, everything fails. If it answers either way, the job silently works from the wrong place, which is worse.

PATH is minimal. python is not found, or a different python is found. Always use absolute paths in a crontab.

No locale. Number and date parsing changes under you. A comma that was a decimal separator becomes a thousands separator, and prices come out wrong by a factor of a thousand with no error at all.

The three fixes

Set variables at the top of the crontab. Simple, and they apply to every line:

http_proxy=http://198.51.100.14:8080
https_proxy=http://198.51.100.14:8080
HTTP_PROXY=http://198.51.100.14:8080
HTTPS_PROXY=http://198.51.100.14:8080
no_proxy=localhost,127.0.0.1
LANG=en_GB.UTF-8
PATH=/usr/local/bin:/usr/bin:/bin

15 3 * * * /opt/jobs/venv/bin/python /opt/jobs/katalog.py >> /var/log/katalog.log 2>&1 ```

Note: crontab assignments are literal. PATH=$PATH:/opt/bin does not expand; you get a literal dollar sign.

Source a file in a wrapper. Better when the same settings are needed by several things:

15 3 * * * . /opt/jobs/hop.env && /opt/jobs/venv/bin/python /opt/jobs/katalog.py

Read the settings inside the program. Best of the three, and the one I would choose. The program reads its own config file and does not depend on the environment at all, so it behaves identically from cron, from a shell, and from a unit file.

Redirect the output or lose it

15 3 * * * /path/job.py >> /var/log/job.log 2>&1

Without a redirect, cron mails the output to the local user. On most machines nothing reads that mailbox, so the output is effectively discarded and a failing job is silent.

2>&1 matters as much as the first half: errors go to standard error, which is exactly the part you want to keep.

Overlapping runs

cron will happily start a job while the previous one is still going. Two collection jobs against one target at once is double the rate you planned.

15 3 * * * /usr/bin/flock -n /tmp/katalog.lock /opt/jobs/katalog.sh

flock -n exits immediately if the lock is held. That single addition prevents a whole category of mysterious rate problems.

Timezone

cron uses the system timezone unless told otherwise. On a server set to UTC, 0 3 * * * is three in the morning UTC, which may be the middle of the target's busy afternoon.

CRON_TZ=Europe/Berlin
0 3 * * * /path/job.sh

Supported by most modern cron implementations. Where it is not, do the arithmetic and write down what you did.

systemd timers instead

If the machine has systemd, timers are better for anything that matters: real logs, dependency ordering, an accurate record of whether the last run succeeded, and per-service environment. The unit page covers the setup.

The one feature with no cron equivalent is Persistent=true, which runs a missed job after a reboot instead of skipping it silently.

Confirming it works

Put the check inside the job:

seen = client.get("https://api.ipify.org", timeout=15).text.strip()
log.info("выходим через %s", seen)
if seen == LOCAL_ADDRESS:
    raise SystemExit("идём напрямую, прогон отменён")

That line in the log every night answers the question permanently, and the exit means a misconfigured schedule fails loudly instead of producing a night of data from the wrong place. It also catches the other end of the problem: an access period that quietly ended overnight looks exactly like a cron bug until you read that line. Worth a calendar reminder a week before your access renews.
