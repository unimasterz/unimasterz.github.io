Wirebound / Runtime and machine

Docker: build time and run time are separate problems

Two questions people ask as one. The container needs settings while installing packages, and your program needs them while running. Different mechanisms, different risks.

sponsor

Two problems

WhenMechanismCredential risk
build--build-arg, or daemon configrecorded in image history
run--env-file, -enone if the file stays outside the image

Almost every confused question about this is really one of these two being answered with the other's mechanism.

Run time, which is what most jobs need

docker run --rm --env-file ./hop.env moj-obraz
# hop.env, в .gitignore и не копируется в образ
http_proxy=http://user:pass@198.51.100.14:8080
https_proxy=http://user:pass@198.51.100.14:8080
HTTP_PROXY=http://user:pass@198.51.100.14:8080
HTTPS_PROXY=http://user:pass@198.51.100.14:8080
no_proxy=localhost,127.0.0.1,::1

The file lives on the host, never enters the image, and can be changed without rebuilding.

In compose:

services:
  sbor:
    image: moj-obraz
    env_file: [./hop.env]

Build time

docker build \
  --build-arg http_proxy=http://198.51.100.14:8080 \
  --build-arg https_proxy=http://198.51.100.14:8080 \
  -t moj-obraz .

These are recognised without being declared in the Dockerfile, and they apply to RUN steps so package installs work.

Never put credentials in a build argument

Build arguments are recorded in the image metadata. Anyone with the image can read them:

docker history --no-trunc moj-obraz | grep -i proxy

If the hop needs credentials at build time, use a bound address for the build machine, which most IPv4 packages support alongside a login, or a build secret, which is mounted for one step and not recorded:

# syntax=docker/dockerfile:1.7
RUN --mount=type=secret,id=hop \
    export $(cat /run/secrets/hop | xargs) && pip install -r requirements.txt
docker build --secret id=hop,src=./hop.env -t moj-obraz .

The daemon, for pulling images

Neither of the above affects docker pull. The daemon is a separate process with its own configuration:

# /etc/systemd/system/docker.service.d/proxy.conf
[Service]
Environment="HTTP_PROXY=http://198.51.100.14:8080"
Environment="HTTPS_PROXY=http://198.51.100.14:8080"
Environment="NO_PROXY=localhost,127.0.0.1,registry.internal"
sudo systemctl daemon-reload && sudo systemctl restart docker

Three separate places, and people routinely set one and expect all three to work.

The networking trap

A container has its own network view. If the hop is reachable only from the host, the container cannot see it no matter how correct the settings are.

# проверять изнутри контейнера, не с хоста
docker run --rm --env-file ./hop.env moj-obraz curl -s https://api.ipify.org

If that fails while the same command works on the host, the problem is reachability, not configuration. Options: host networking, or a hop address the container can actually reach.

localhost inside a container means the container, not the host. A hop on 127.0.0.1:3128 on the host is invisible; use host.docker.internal or the host's real address.

A Dockerfile that behaves in both worlds

FROM python:3.12-slim

ARG http_proxy ARG https_proxy ARG no_proxy

WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# сборочные значения не должны протечь в работу ENV http_proxy= https_proxy= no_proxy=

CMD ["python", "katalog.py"] ```

That last ENV line clears the build values so the running container uses only what you pass at run time. Without it, a build argument can linger and quietly override your run time file.

Confirming it works

docker run --rm --env-file ./hop.env moj-obraz \
  sh -c 'env | grep -i proxy; curl -s https://api.ipify.org; echo'

Prints the settings the container actually received and where its traffic comes out, in one command. Run it before trusting a scheduled container.
