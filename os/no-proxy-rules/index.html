The bypass list: what actually matches and what silently does not

no_proxy is the setting most likely to work on your machine and fail on the server, because every implementation invented its own matching rules. Here they are, side by side.

sponsor

The problem in one line

There is no specification for no_proxy. Every client implemented what seemed reasonable, and they disagree about almost everything.

The two rows worth memorising: CIDR notation works in curl and nowhere else in this table, and the *. wildcard works in Go and not in the others.

A bare domain does not always cover subdomains

In Go, no_proxy=example.com does not match api.example.com. In curl and requests it does. This single difference accounts for a large share of "it bypasses on my laptop and not on the server" reports.

The portable form is to list both:

export no_proxy="example.com,.example.com,localhost,127.0.0.1,::1"

Verbose and it behaves the same everywhere.

Things that catch people

Spaces after commas. Some implementations trim, some treat the space as part of the hostname. Write the list with no spaces.

Uppercase. Matching is case insensitive for hostnames in most implementations, but not all handle an uppercase entry the same way. Keep entries lowercase.

Addresses versus names. An entry of 10.0.0.5 does not match a request to internal.example even if that name resolves to 10.0.0.5. Matching happens on the string in the url, before resolution. If you reach a host by name, put the name in the list.

IPv6. Needs ::1 explicitly; localhost does not always cover it.

The empty value. no_proxy="" means an empty list in most implementations, and in a few it means something is set. If you want no bypass, unset the variable.

Puppeteer, PlaywrightChrome's own list, different syntax

Chrome's list uses semicolons in Puppeteer's flag and commas in Playwright's option, for the same underlying feature. It also has its own tokens, notably <-loopback>.

Testing yours

Do not reason about it. Ask:

for h in example.com api.example.com localhost 10.0.0.5; do
  printf '%-20s ' "$h"
  curl -s -o /dev/null -w "%{http_code}\n" -m 8 "http://$h/" 2>/dev/null || echo "нет"
done

Better, ask an echo service through each name you care about and compare the answers. Whichever hosts report your own address are bypassing; the rest are not.

The habit that avoids all of this

For anything unattended, do not use the bypass list. Route explicitly in code: one client configured, one not, and the call site picks.

It is more typing and it behaves identically on every machine, in every language, forever. The bypass list is convenient for interactive use and is a portability trap in a scheduled job.
