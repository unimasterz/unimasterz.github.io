Environment variables: exact precedence and the casing problem

There is no standard here, only a widespread convention that every implementation follows slightly differently. This page is the convention plus the known deviations.

sponsor

The variables

VariableApplies to
http_proxyplain http targets
https_proxyencrypted targets
all_proxyeverything, where supported
no_proxythe bypass list
ftp_proxyftp, rarely relevant now

Each also exists in upper case, and the two are not interchangeable.

Why both cases exist

HTTP_PROXY in upper case collides with a CGI convention: a request header called Proxy arrives in a CGI environment as HTTP_PROXY. That means a remote visitor could set it by sending a header, and a server-side script reading it would route its own outbound traffic wherever the visitor said.

This was a real vulnerability, and the consequence is a permanent split:

ToolReads
curllowercase http_proxy only, both cases for https_proxy
Python requestsboth, lowercase wins where both are set
Node global fetchneither
Goboth, and rejects HTTP_PROXY when it detects a CGI environment
Javaits own system properties, not these at all

The safe habit: set both cases to the same value, and never rely on which one wins.

export http_proxy="http://198.51.100.14:8080"
export https_proxy="$http_proxy"
export HTTP_PROXY="$http_proxy"
export HTTPS_PROXY="$http_proxy"
export no_proxy="localhost,127.0.0.1,::1"
export NO_PROXY="$no_proxy"

Precedence, in general

Nearly every client follows this order, and where one deviates the per-client page says so.

  1. A value passed explicitly in code, per call
  2. A value set on the client or session object
  3. Environment variables
  4. Nothing, which means direct

The important exception is requests, where the environment beats the session dictionary unless you turn it off. That inversion is the single most surprising precedence rule in this reference.

`https_proxy` usually holds an `http://` url

The variable name describes the target scheme; the value describes how to reach the hop. https_proxy=http://... is normal and correct. https_proxy=https://... means the hop itself speaks TLS to you, which is rare.

Finding out what is actually set

env | grep -i proxy

Run it as the user and in the environment the job actually uses. A variable set in your interactive shell profile is invisible to cron, to a unit file, and to a container, and the reverse is also true.

For a running process:

tr '\0' '\n' < /proc/$(pgrep -f moj-skript)/environ | grep -i proxy

That reads what the process actually received at start, which is the only version that matters and is often not what you assumed.

Where they come from and where they do not

Set inApplies to
~/.bashrc, ~/.profileinteractive shells only
/etc/environmentmost login sessions, not cron on every system
a unit file Environment=that service only
docker run --env-filethat container only
a .env fileonly if something loads it, nothing does automatically

The cron case catches people constantly and has its own page.

Turning them off

Because a stray variable can silently redirect a job, unattended work is usually better off ignoring the environment and setting everything explicitly:

s = requests.Session(); s.trust_env = False       # Python requests
c = httpx.Client(trust_env=False)                 # httpx
client = axios.create({ proxy: false })           # axios с агентами

Then nothing a shell profile does can change how the run behaves, which is what you want for something that must produce the same result every night.

Confirming which one won

The only reliable check is to ask where the traffic came out:

curl -s https://api.ipify.org; echo

with no flags at all. That answer is the environment's answer, and comparing it against your machine's own address tells you in one line whether anything is in effect.
