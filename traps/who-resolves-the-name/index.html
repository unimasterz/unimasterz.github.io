Who resolves the name, and how to prove which side did

One letter decides it. Ten seconds proves it.

sponsor

What actually changes

Three things, and only the first is the one people mention.

Who saw the request. If your machine resolves, your resolver and everything on the path to it saw which host you were about to visit, even though the traffic itself went elsewhere.

Which server you reached. Large sites answer differently depending on where the question came from. Your resolver and the far end's resolver may return different addresses for the same name, so the two paths reach different machines.

Whether internal names work. A hostname that only resolves inside the far end's network fails if your side does the lookup, and works if the far end does.

Proving it

Two terminals, ten seconds, no opinions involved.

sudo tcpdump -n port 53

Run one request in the other terminal. A query for your target hostname means your machine resolved it. Silence means the far end did.

-n matters: without it tcpdump resolves addresses to names and generates its own queries, which muddies exactly the thing you are watching.

On a machine with a local resolver cache, the first request may be answered from cache and show nothing. Flush it or use a hostname you have not visited.

The one letter

Written asResolved by
socks5://host:1080your machine
socks5h://host:1080the far end

The h stands for hostname: the name is passed along instead of an address.

Most people who reach for this family want the second and type the first. And not every client implements both spellings, which is why the table on each client page says what that client actually does.

For plain http

For an ordinary http hop the question is settled by the request shape: your client sends the full url and the hop resolves it. So plain http hops resolve at the far end by default, and this whole question only arises for the other family.

The exception is a client that resolves first to validate the hostname, then sends the request. Some libraries do this, and then a query appears on the wire even though the hop would have handled it. If your capture shows a query you cannot explain, that is usually why.

Why it changes results

A catalogue served from several regions answers according to where the request appears to come from, and the resolution step is part of that. A run where your side resolves may reach a different server from a run where the far end does, with different content and different prices, from the same address and the same code.

If your job compares results over time, this is worth pinning deliberately instead of leaving it to whichever spelling somebody typed.

Pinning it when you need to

curl --resolve primer.example:443:203.0.113.10 -x "$LINE" https://primer.example/

--resolve skips resolution entirely and uses the address you gave. Useful for testing a specific server, and for reproducing a result somebody else got.

The check worth keeping

Once, when you set up a job, and written down next to the config:

sudo timeout 10 tcpdump -n port 53 -c 20 &
curl -x "$LINE" -s -o /dev/null https://primer.example/
wait

Empty output means the far end resolves. Queries mean your machine does. Record which one it was, because in six months nobody will remember, and the answer changes what the numbers mean. Where the job needs the far end to resolve, check that the entry actually speaks that family: SOCKS5 access with remote name lookups is usually offered on the same address as the http port.
