Connection reuse: when it survives the hop and when it does not

Setting up an encrypted connection through a hop costs a tunnel plus a handshake. Paying that once per session is normal; paying it three thousand times in a run is most of the run.

sponsor

The cost

For an encrypted target through a hop, a new connection costs:

  1. reaching the hop
  2. the tunnel request and its answer
  3. the handshake with the real target

Roughly two to four round trips before a single byte of your request moves. On a path with 60 milliseconds of latency that is a fifth of a second per connection, every time.

Three thousand pages with no reuse is ten minutes of pure setup.

Measuring reuse

curl -x "$LINE" -sv -o /dev/null \
  https://primer.example/a https://primer.example/b https://primer.example/c 2>&1 \
  | grep -E "Connected to|Re-using"

One Connected to followed by two Re-using is correct. Three Connected to means nothing is being reused.

From the timings, the same answer:

curl -x "$LINE" -s -o /dev/null -w "tls=%{time_appconnect} all=%{time_total}\n" https://primer.example/

If the handshake is a large share of the total on every call, connections are not being kept.

The usual cause

A client created inside the loop:

# заново на каждый вызов: пул создаётся и выбрасывается
for u in urls:
    r = requests.get(u, proxies=P)

# один пул на весь прогон with requests.Session() as s: s.proxies = P for u in urls: r = s.get(u) ```

Same shape in every language: a new client means a new pool, and a new pool means full setup on the first call.

The second cause, which is quieter

The pool exists and is too small.

Go's default of two is the one that surprises people most. Twenty goroutines against one host with the default open and close connections continuously, and the symptom looks exactly like a slow target.

What breaks reuse even when configured

A hop that closes after each request. Some do. The response carries Connection: close, and your client obeys. Nothing you set will change it; the reuse has to come from their side.

Gaps in the run. If your job sleeps two minutes between batches, idle connections are closed by then and you pay setup again for each batch. Either shorten the gap or accept the cost.

Rotating addresses per request. Each address is a different connection, so per-request rotation means no reuse at all, by construction. This is the hidden cost of rotating on every call and a reason to hold an address per worker instead. That arrangement wants one entry per worker from a fixed pool, not something that changes underneath you.

Redirects across hosts. A redirect to a different host needs a new connection regardless.

Idle timeouts

# Python
HTTPAdapter(pool_maxsize=20, pool_block=False)

# Go IdleConnTimeout: 90 * time.Second

# Node undici new ProxyAgent({ uri: line, connections: 20, keepAliveTimeout: 30_000 }) ```

Set the idle timeout below whatever the hop uses, or your client keeps offering connections the far end has already closed, and you get an occasional reset that looks random.

The thing worth measuring once

For a long job, count connections opened against requests made:

ss -tn | grep -c ESTAB

Sample it a few times during a run. A number that climbs steadily is a leak. A number that matches your worker count is healthy. A number far below your worker count means workers are queueing for connections, and the pool is your limit.

Confirming it works

Run the curl comparison above at the start of a project and note the answer. It takes one command, and it is the difference between a run that takes twelve minutes and one that takes forty for identical work.
