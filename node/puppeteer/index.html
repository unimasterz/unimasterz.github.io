Puppeteer: where the setting lives and what the browser ignores

One flag, one browser-wide value, and no credentials. The three ways around the credential problem, and what each costs. Tested against Puppeteer 22.

The setting

import puppeteer from "puppeteer";

const br = await puppeteer.launch({ args: [ "--proxy-server=http://198.51.100.14:8080", "--proxy-bypass-list=<-loopback>", ], }); const page = await br.newPage(); await page.goto("https://example.com", { waitUntil: "domcontentloaded" }); ```

Browser-wide. Every page and every context in this browser uses it. Unlike Playwright, there is no per-context value.

Credentials in the flag do nothing

--proxy-server=http://user:pass@host:8080 is accepted and the credentials are ignored. Chrome then shows an authentication dialog, which no page-level code can dismiss.

The three ways around it

A bound address. Your machine is on the provider's allowlist, so nothing needs authenticating and the flag works exactly as written. Simplest, and it is the reason bound access exists, so it is worth checking whether your package supports it before building anything: most IPv4 packages do.

page.authenticate. Puppeteer can answer the dialog:

await page.authenticate({ username: "user", password: "pass" });

This works, with two caveats worth knowing before you rely on it. It is per page, so every new page needs the call, and forgetting one gives you a page that hangs on a dialog. And it interacts awkwardly with request interception on some versions, where enabling interception can swallow the authentication challenge.

A local relay. A small process on localhost that holds the credentials and talks to the hop. The browser points at localhost with no credentials at all:

"--proxy-server=http://127.0.0.1:3128"

More moving parts, and it is the most robust of the three: it works identically for every browser, every version, and every tool on the machine, and the credentials live in exactly one place.

Several identities means several browsers

const brA = await puppeteer.launch({ args: ["--proxy-server=http://a:8080"] });
const brB = await puppeteer.launch({ args: ["--proxy-server=http://b:8080"] });

Two processes, two sets of memory. Where Playwright gives you two contexts in one process, Puppeteer gives you two browsers. On a machine running many identities that difference adds up quickly, and it is the main practical reason to prefer Playwright for that kind of work.

Note that createIncognitoBrowserContext isolates storage but not the route: contexts inherit the browser's flag and cannot change it.

Bypass

"--proxy-bypass-list=<-loopback>;*.internal;127.0.0.1"

Semicolon separated here, unlike the comma separated form Playwright takes. <-loopback> is a special token meaning loopback should also go through the setting; by default Chrome exempts it. Most jobs want loopback exempted, so include it only if you know you need it.

Timeouts

await puppeteer.launch({ timeout: 30_000 });
page.setDefaultNavigationTimeout(30_000);
await page.goto(url, { timeout: 45_000, waitUntil: "domcontentloaded" });

waitUntil: "networkidle0" is popular in examples and is a poor default for collection: a page with any polling never reaches network idle and you wait for the full timeout on every single page.

Watching the underlying calls

page.on("response", async (r) => {
  if (r.url().includes("/api/")) console.log(r.status(), r.url());
});

Worth doing on any new target before committing to a browser at all. Finding the call behind the page usually means you can drop the browser and the whole credential problem with it.

Confirming it works

await page.goto("https://api.ipify.org");
console.log("puppeteer выходит через", (await page.evaluate(() => document.body.innerText)).trim());

If you are using page.authenticate, run the check on a page created the same way your real code creates pages. A check on a page that happened to get the call is not a check.
