Playwright: browser level, context level, and which overrides which

The one tool here that lets you hold several separate routes inside a single browser process. The replacement rule between the two levels is the thing to get right. Tested against Playwright 1.44.

The two levels

import { chromium } from "playwright";

const br = await chromium.launch({ proxy: { server: "http://198.51.100.14:8080", username: "user", password: "pass" }, }); const page = await br.newPage(); await page.goto("https://example.com"); ```

Credentials are separate keys, never in the server string. No encoding, no dialog, no relay. This is the cleanest handling of credentials in any browser tool covered here.

Per context, and why it matters

const br = await chromium.launch({ proxy: { server: "http://per-context" } });

const a = await br.newContext({ proxy: { server: "http://a.example:8080", username: "u1", password: "p1" }, }); const b = await br.newContext({ proxy: { server: "http://b.example:8080", username: "u2", password: "p2" }, }); ```

Two contexts, two routes, separate cookies and storage, one browser process. That is a large saving in memory over launching two browsers, and it is the reason to reach for Playwright over Selenium when you need several identities. The other half of that arrangement is one address per context, held for the life of the profile, which is what a per-address pool is for.

The context value does not inherit anything

A context that sets server and omits username does not pick up the credentials from launch. It replaces the whole object. Write every context's proxy out in full, or build it from one source in code.

The placeholder at launch is deliberate: on some engine and version combinations, a browser launched with no proxy at all refuses per-context values. Launching with a dummy server costs nothing and removes the question.

Persistent contexts

const ctx = await chromium.launchPersistentContext("./profiles/de-01", {
  proxy: { server: "http://198.51.100.14:8080", username: "u", password: "p" },
});

Here launch and context are the same call, so there is only one level and no replacement rule. This is the right shape when a profile is meant to persist between runs.

Bypass

proxy: {
  server: "http://198.51.100.14:8080",
  bypass: "localhost,127.0.0.1,*.internal",
}

Comma separated, no spaces around the commas. Leading dots and wildcards behave as Chrome's bypass list does, since that is what it becomes.

Worth adding loopback so the driver's own traffic does not go through the hop.

Timeouts

const br = await chromium.launch({ proxy, timeout: 30_000 });      // запуск браузера
ctx.setDefaultNavigationTimeout(30_000);
ctx.setDefaultTimeout(15_000);
await page.goto(url, { timeout: 45_000, waitUntil: "domcontentloaded" });

Four different clocks and they cover different things: starting the browser, navigating, waiting for elements, and one navigation specifically.

waitUntil: "domcontentloaded" is usually what a collection job wants. The default waits for the load event, which on a page with slow third-party resources can add many seconds for content you are not reading.

Watching what the page actually requests

page.on("request", (r) => console.log(r.method(), r.url()));
page.on("response", (r) => console.log(r.status(), r.url()));

This is how you find the underlying call that a page makes, which is often a much better collection target than the rendered page. Two lines, and it frequently removes the need for the browser entirely.

Confirming it works

for (const [imya, ctx] of [["a", a], ["b", b]]) {
  const p = await ctx.newPage();
  await p.goto("https://api.ipify.org");
  console.log(imya, (await p.innerText("body")).trim());
  await p.close();
}

Check every context, not just one. A context that silently fell back to the launch value or to direct looks perfectly healthy until asked.
