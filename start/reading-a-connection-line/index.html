Anatomy of the line your provider hands you

A provider gives you something like user:pass@198.51.100.14:8080. Five pieces, and four of them change behaviour. This page takes the line apart so the per-client tables make sense.

sponsor

The shape

Written out in full, the line your client wants looks like this:

scheme://user:password@host:port

Providers rarely hand it over in that form. More often you get the four values in a panel and assemble the line yourself, which is where the mistakes start.

PieceDecidesCommon mistake
schemehow the client talks to the hop, and who resolves namescopying https:// because the target is encrypted
user, passwordwhether you are allowed throughspecial characters left unescaped
hostwhich machine you reachusing the panel's display name instead of the address
portwhich service on that machine answersassuming the port implies the scheme

The scheme is not the target's scheme

This is the single most common error, and it is worth stating flatly.

The scheme in the line describes how you reach the hop, not what the destination is. Fetching an encrypted page through a plain hop is completely normal and is what almost everyone is doing.

# correct for nearly every provider
http://user:pass@198.51.100.14:8080

# wrong unless the hop itself speaks TLS to you, which is rare https://user:pass@198.51.100.14:8080 ```

In Python this bites in a specific place, because the mapping is keyed by the target's scheme while both values describe the hop:

proxies = {
    "http":  "http://user:pass@198.51.100.14:8080",
    "https": "http://user:pass@198.51.100.14:8080",
}

Both values are http://. Everyone puts https:// in the second slot once.

The two characters that move name resolution

For the other family of schemes, one trailing letter decides which side looks up your hostnames.

Written asName resolved byUse when
socks5://your machineyou want local resolution deliberately
socks5h://the far endyou want the lookup to happen at the hop

The h stands for hostname, meaning the hostname is passed along instead of an address. Most people who reach for this family want socks5h and type socks5, then spend an evening wondering why the results look like they came from home.

Not every client implements both spellings. The per-client pages say which.

Confirm instead of assume

Whichever spelling you use, run probe two once. Watch port 53 while a request runs and you will know for certain, for your client and your version, in ten seconds.

Ports carry a habit, not a rule

You will see 8080, 3128, 8000 and 1080 most often. The last one is traditionally the other family. All of this is convention and none of it is enforced: a provider can put anything on any port.

If you have a pair with no other information, try both ways and see which answers:

curl -x http://198.51.100.14:8080  -s -o /dev/null -w "http  %{http_code}\n" https://example.com
curl -x socks5h://198.51.100.14:1080 -s -o /dev/null -w "socks %{http_code}\n" https://example.com

The wrong scheme against a live port often hangs instead of refusing, which reads like a network fault and is not one.

Characters that break the line

Credentials go into a url, and a url has reserved characters. A password containing @, :, /, # or ? will be parsed as structure instead of as your password.

Percent-encode the two fields before assembling:

from urllib.parse import quote

u = quote("user", safe="") p = quote("pa:ss@word", safe="") line = f"http://{u}:{p}@198.51.100.14:8080" ```

An @ in a password is the classic. The parser reads everything before the last @ as credentials, so the line still looks valid and simply points somewhere unintended.

Two ways to avoid the problem entirely: ask the provider for credentials without punctuation, or pass user and password as separate arguments where the client supports it, which several do.

Where the line should live

Not in your source, and not in a file that gets committed.

# settings.ini, listed in .gitignore
[hop]
host = 198.51.100.14
port = 8080
user = whoever
pass = whatever

Read it at startup, assemble the line in one place, and pass that one value around. When something needs changing there is a single edit, and the line never appears in a diff.

If the credentials have already been committed at some point, treat them as public and change them. Rewriting repository history is slower than a password reset and less reliable.

Two ways in, and both can be on at once

Providers usually offer either credentials or a bound address, and often both.

Credentials. You send a user and password with each connection. Works from anywhere, which is what you want when the machine you connect from changes.

Bound address. The provider records the address you connect from and accepts only that one. Nothing to put in the line at all, which is why a script that worked on a laptop returns a refusal the moment it runs on a server: the connection now arrives from somewhere the provider has not been told about.

Most panels accept several bound addresses at once, so a laptop and a server can both be listed. Private IPv4 addresses usually offer both modes on the same address, which is convenient while you are still deciding which one your job needs. Worth knowing that a package's thread limit is usually shared across them, so two entries do not double the capacity.
