How every entry here was checked

Every claim on this site came out of running something and reading the result, so this page is the procedure itself: the bench, the four probes, and what each one proves. Repeat any entry yourself in about a minute, and disagree with it if your version behaves differently, because your machine today beats my machine last month.

Why a reference and not another guide

Most writing about proxies answers the question once, in general, and leaves you to discover that your particular library disagrees. The interesting differences are never in the concept. They are in the eleven lines of behaviour that separate requests from httpx, or axios from global fetch.

So each page here answers the same five questions about one specific client:

  1. Where does the setting go, and what is its scope.
  2. Does an environment variable override it, and which one wins.
  3. Which side resolves the hostname.
  4. What happens to certificate verification for encrypted targets.
  5. What is the trap.

If a page cannot answer all five, the missing ones are marked instead of guessed.

The bench

Nothing exotic. The point is that you can rebuild it.

PieceWhat was used
Machinesone Debian 12 box, one Windows 11 laptop
Routea private datacenter IPv4 address with HTTP and SOCKS5 on separate ports
Echo targeta service that returns the calling address as plain text
Observertcpdump on the client side, filtered to port 53 and to the hop
Clockcurl -w timings, second call onward

The route was a package of private datacenter addresses with both protocol families on the same entry, of the kind sold per address instead of per gigabyte, so nothing in the measurements is distorted by a traffic meter.

Two machines matter more than it sounds. A surprising number of published claims are true on one operating system and wrong on the other, and Windows in particular resolves names and reads settings through a different path.

The four probes

Every page uses the same four probes. When an entry says "the library does X", one of these produced that answer.

Probe one: did the request take the route at all

Ask something that reports the calling address back, once through the setting and once without it. Two different answers means the setting applied.

curl -x http://user:pass@198.51.100.14:8080 -s https://api.ipify.org; echo
curl -s https://api.ipify.org; echo

This is the probe people skip, and skipping it is why some scripts run for months going direct while their author believes otherwise.

Probe two: which side resolved the name

Watch port 53 on the client while the request runs. If you see a query for the target hostname, your machine resolved it. If you see nothing, the resolution happened at the far end.

sudo tcpdump -n -i any port 53

Run the request in another terminal. This single observation settles an argument that appears in every second thread on the subject, and it settles it for your machine and your version instead of in general.

Probe three: what the tunnel did

For an encrypted target, add -v and look for the CONNECT line, then for the certificate the client accepted.

curl -x http://198.51.100.14:8080 -v https://example.com 2>&1 | grep -E "CONNECT|subject:|issuer:"

The issuer should be a public certificate authority. If it is the hop itself, the connection is being read on the way through, and that changes what you can say about it.

Probe four: is the connection being reused

Ask for two urls in one invocation and compare the connection numbers.

curl -x http://198.51.100.14:8080 -sv -o /dev/null \
  https://example.com/a https://example.com/b 2>&1 | grep -E "Re-using|Connected to"

Re-using existing connection on the second means the client kept it. A second Connected to means it did not, and you are paying for a new handshake on every call.

Repeat the timing measurement twice

The first call to a host pays for name resolution and a handshake. Quote the second one. Most published speed comparisons quote the first and then wonder why nobody can reproduce them.

What is deliberately not here

No rankings, no scores, no "best" list. Those age badly and they describe the writer's week, not your job.

No claims about what a particular website does. Sites change, and a reference that names them is wrong within a quarter.

No numbers without the command that produced them. If a figure appears on a page, the way to reproduce it appears next to it.

When an entry is wrong

Library behaviour changes. An entry here describes a version, and the version is named on the page. If your result differs, trust your result: you ran it today, on your machine, against your target.

The probes above are the part worth keeping. The tables are the part that will need updating.
