Wirebound / Command line

ssh: turning a shell into a local hop

If you have shell access somewhere, you already have a working hop and did not need to install anything. Useful for testing, for reaching things from a specific place, and as a stopgap. Tested against OpenSSH 9.6.

The five answers

QuestionAnswer for ssh forwarding
Where the setting goesa local port your programs point at
Environment overridenot applicable
Who resolves the namethe far end, in dynamic mode
Certificatesuntouched, end to end as usual
The trapa tunnel dies quietly and nothing tells you

Dynamic: a general purpose local hop

ssh -D 1080 -N -q user@server.example

Now socks5://127.0.0.1:1080 works for anything on your machine.

curl -x socks5h://127.0.0.1:1080 https://api.ipify.org; echo

The h matters as everywhere: with it, hostnames are resolved at the server end. In dynamic mode that is usually the whole point.

-N means do not run a command, -q suppresses the banner. Without -N you get a shell you did not want.

Local: one specific service

ssh -L 5433:db.internal:5432 -N user@server.example

Now localhost:5433 reaches db.internal:5432 as seen from the server. For one service this is simpler than dynamic mode and does not require the client to speak any particular scheme.

Remote: the other direction

ssh -R 8080:localhost:3000 -N user@server.example

The server's port 8080 reaches your local port 3000. Occasionally useful for showing somebody a local thing; requires GatewayPorts on the server for anything beyond the server's own loopback.

Keeping it alive

A tunnel that dies leaves your programs connecting to a closed port, and the failure looks like the target being down.

ssh -D 1080 -N -q \
    -o ServerAliveInterval=30 \
    -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    user@server.example

ExitOnForwardFailure is the important one. Without it, ssh happily connects even when it could not open the forward, and you have a live session forwarding nothing.

For anything unattended, use autossh or a supervisor:

autossh -M 0 -f -N -D 1080 \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -o ExitOnForwardFailure=yes user@server.example

Or a unit file, which is what I would use on a server:

[Service]
ExecStart=/usr/bin/ssh -N -D 1080 -o ServerAliveInterval=30 \
  -o ExitOnForwardFailure=yes user@server.example
Restart=always
RestartSec=10

Config file instead of flags

# ~/.ssh/config
Host hop
    HostName server.example
    User user
    DynamicForward 1080
    ServerAliveInterval 30
    ExitOnForwardFailure yes
    IdentityFile ~/.ssh/hop_ed25519
ssh -N hop

Same benefit as everywhere: the settings live in one file, the command is short, and nothing lands in your shell history.

What this is good for, and what it is not

Good for: testing how a target behaves from a specific place, reaching internal services, a stopgap when you need one route right now.

Not good for: running many parallel jobs. Everything shares one connection to one server, so the far end sees one address and the tunnel is a single point that carries all of it. For a job that needs volume or several distinct origins, this is the wrong shape and a real pool is the right one. A dozen addresses from somewhere like an ordinary provider panel costs less than the afternoon you will spend keeping four tunnels alive.

Confirming it works

ss -tlnp | grep 1080                                    # слушает ли порт
curl -x socks5h://127.0.0.1:1080 -s https://api.ipify.org; echo

Check the port first. A dead tunnel and a misconfigured client look identical from the curl output alone, and the first command distinguishes them in a second.
