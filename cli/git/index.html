git: per remote, per host, and why credentials break

Two protocols with completely separate mechanisms, and the credential helper is a third thing that breaks in its own way. Tested against git 2.45.

sponsor

The five answers

QuestionAnswer for git over https
Where the setting goeshttp.proxy, globally or per url
Environment overrideyes, and config beats it
Who resolves the nameyour machine, via curl
Certificatesverified against the real target
The trapssh remotes ignore all of it

Per host, which is what you usually want

# всё через один узел
git config --global http.proxy http://198.51.100.14:8080

# только для одного хоста git config --global http.https://github.com/.proxy http://198.51.100.14:8080

# а этот напрямую git config --global http.https://git.internal/.proxy "" ```

The per-url form is the useful one. The trailing slash matters and the match is by prefix, so https://github.com/ covers everything under it.

An empty value means direct for that host, which is how you carve out an exception without a bypass list.

ssh remotes are a different world

git clone git@github.com:user/repo.git

None of the http.* settings apply. ssh has its own mechanism, in its own config:

# ~/.ssh/config
Host github.com
    ProxyCommand nc -X connect -x 198.51.100.14:8080 %h %p

or with newer OpenSSH:

Host github.com
    ProxyJump user@bastion.example

This is the single most common confusion with git: a working http.proxy and an ssh remote, and nothing happens. Check which protocol your remote uses before debugging anything else:

git remote -v

Credentials

The credential helper runs before the network call and stores what it gets. Two things go wrong.

The helper caches a failure. A clone that failed for network reasons can leave a bad entry, and every subsequent attempt fails instantly with an authentication error that has nothing to do with your credentials. Clear it:

git credential-cache exit
printf 'protocol=https\nhost=github.com\n' | git credential reject

The helper prompt never appears. In a non-interactive environment the helper wants to open a window or read a terminal, finds neither, and the operation hangs or fails obscurely. For automated use, set the helper explicitly or use a token in the url.

Timeouts

git has no proxy-specific timeouts, but two settings save unattended jobs:

git config --global http.lowSpeedLimit 1000
git config --global http.lowSpeedTime 60

Abort if the transfer falls below 1000 bytes per second for 60 seconds. Without this a stalled clone can hang until something else kills it, which on a scheduled job means the whole job hangs.

Large clones

git clone --depth 1 --single-branch https://github.com/user/repo.git
git config --global http.postBuffer 524288000

--depth 1 is the setting that actually matters through a constrained path: a shallow clone of a large repository is a fraction of the transfer.

http.postBuffer is the standard advice for pushes that fail with an unexpected disconnect. It genuinely helps and it is a workaround, so if you need it, note why next to it.

Debugging

GIT_CURL_VERBOSE=1 GIT_TRACE=1 git clone https://github.com/user/repo.git 2>&1 | head -40

Because git uses curl underneath, this gives you the same CONNECT line and certificate detail as running curl by hand. It settles whether the route is being used in one command.

Confirming it works

git config --get-regexp '^http\..*proxy'
GIT_CURL_VERBOSE=1 git ls-remote https://github.com/git/git 2>&1 | grep -i "connect\|proxy" | head -5

ls-remote is the cheapest real operation: it contacts the server, transfers almost nothing, and tells you whether the whole path works. Run it from the build machine as well as your own, since the two often reach the outside through different entries of the same address package.
