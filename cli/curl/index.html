curl: every flag that changes the route, and what each proves

The tool every other page here uses to check its claims. Worth knowing properly, because a fault you can reproduce in curl is a fault that has nothing to do with your code. Tested against curl 8.7.

The five answers

QuestionAnswer for curl
Where the setting goes-x, or a config file, or the environment
Environment overrideyes, and -x beats it
Who resolves the nameyour machine, unless the scheme says otherwise

The flags that matter

FlagWhat it does
-x, --proxythe route, with an optional scheme
--proxy-usercredentials without putting them in the url
--noproxycomma separated bypass list
-4, -6force an address family
--resolvepin a hostname to an address, skipping resolution
-vshow the tunnel being set up
-wthe timing numbers
--proxy-insecureskip verification for the hop, not the target
curl -x http://198.51.100.14:8080 --proxy-user user:pass https://example.com

--proxy-user instead of putting credentials in the url avoids percent-encoding entirely, and keeps the password out of the visible part of your command.

What -v actually shows

curl -x http://198.51.100.14:8080 -v https://example.com 2>&1 | grep -E "CONNECT|subject:|issuer:|Proxy"

Three things to look for.

CONNECT example.com:443 proves a tunnel was requested, which means the hop is genuinely in the path for an encrypted target.

issuer: naming a public certificate authority proves the encryption is end to end. If it names the hop, the connection is being read on the way through.

Proxy-Authorization appearing confirms credentials were sent, which distinguishes "wrong password" from "password never sent".

The timing output

curl -x "$LINE" -s -o /dev/null -w \
 "dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} all=%{time_total}\n" \
 https://example.com

Cumulative from zero, so the gaps are the information. The full reading of these is on the traps page, but the short version: a big gap between tls and first is the target thinking, and nothing you configure will change it.

Always take the second measurement

The first call to a host pays for resolution and a cold handshake. Run it twice and quote the second. Most speed claims that nobody can reproduce are first-call numbers.

The shell trap

This is the most common cause of "works in curl, fails in my code" and it works the other way too.

# оболочка съест часть пароля
curl -x http://user:pa$$word@198.51.100.14:8080 https://example.com

# правильно curl -x http://198.51.100.14:8080 --proxy-user 'user:pa$$word' https://example.com ```

Double quotes are not enough: the shell still expands $, backticks and history references inside them. Single quotes, or better, keep it out of the command line altogether:

# ~/.curlrc или отдельный файл
proxy = "http://198.51.100.14:8080"
proxy-user = "user:pa$$word"
curl -K ./hop.conf https://example.com

A config file removes the shell from the equation and keeps the password out of your shell history, which is worth doing for that reason alone.

Precedence

SourceBeats
-x on the command lineeverything
-K config fileenvironment
~/.curlrcenvironment
https_proxy, http_proxynothing above

--noproxy overrides all of them for the hosts it matches. Note that curl reads lowercase http_proxy only, deliberately, to avoid a well-known confusion with a CGI header.

Checking a whole list

while read -r line; do
  printf '%-42s ' "${line##*@}"
  curl -x "$line" -s -o /dev/null -m 12 \
    -w "%{http_code} %{time_total}\n" https://api.ipify.org || echo "нет ответа"
done < spisok.txt

${line##*@} prints only the part after the credentials, so the output is safe to paste into a support ticket. Run this over a fresh list on the day it arrives: on a well run pool everything answers, and if one entry does not, that is the moment to say so. Mine come from IPrazon SOCKS5 and the list has been clean, but I still check.

The other family

curl -x socks5://198.51.100.14:1080  https://example.com   # резолв локально
curl -x socks5h://198.51.100.14:1080 https://example.com   # резолв на той стороне

curl implements both spellings and the distinction is real here, which makes curl the fastest way to check what your library ought to be doing.

Confirming it works

curl -x "$LINE" -s https://api.ipify.org; echo
curl -s https://api.ipify.org; echo

Two different answers means the route applied. This is probe one from the method page, and it is two lines.
