Scrapy: middleware order decides which address wins

Scrapy is the one client here where the setting is a piece of request metadata, processed by a chain you can reorder. That makes it flexible and makes the precedence non-obvious. Tested against Scrapy 2.11.

The mechanism

There is one key and everything else is machinery around it.

def start_requests(self):
    yield scrapy.Request(
        "https://example.com",
        meta={"proxy": "http://198.51.100.14:8080"},
    )

HttpProxyMiddleware reads that key and applies it. If the key is absent, the same middleware falls back to the environment.

Credentials do not go in the meta value in the usual url form. Scrapy expects them as a header, and the middleware builds it for you if you put them in the url once:

# работает: middleware извлечёт и переложит в заголовок
meta={"proxy": "http://user:pass@198.51.100.14:8080"}

After the first request the credentials are moved into Proxy-Authorization and stripped from the meta value. If you later copy that meta into a new request you lose the credentials, which is a surprising and well-known trap.

Copying meta between requests drops the credentials

response.request.meta no longer contains the password after the middleware has run. If you build follow-up requests by copying meta, carry the original line from settings instead of from the previous request.

Per spider, not per project

The clean pattern for most jobs: one middleware that sets the key, configured per spider.

# middlewares.py
class HopMiddleware:
    def __init__(self, line):
        self.line = line

@classmethod def from_crawler(cls, crawler): return cls(crawler.settings.get("HOP_LINE"))

def process_request(self, request, spider): if self.line and "proxy" not in request.meta: request.meta["proxy"] = self.line ```

# settings.py
DOWNLOADER_MIDDLEWARES = {
    "myproject.middlewares.HopMiddleware": 700,
    "scrapy.downloadermiddlewares.httpproxy.HttpProxyMiddleware": 750,
}

The numbers are the whole game. Lower runs first on the way out. Yours at 700 sets the key before the built-in at 750 reads it, which is what you want. Put yours after 750 and it sets a key nobody looks at.

Rotating per request

Because it is a meta key, rotation is a line in your middleware:

def process_request(self, request, spider):
    request.meta["proxy"] = self.next_line(request)

Two cautions.

Rotating per request breaks anything with a session. If your spider logs in, pin the value for that chain of requests instead.

Retries reuse the same request object, so a failed request retried keeps its old value unless you clear it. If you want a retry to go elsewhere, remove the key in your retry handling.

Concurrency

CONCURRENT_REQUESTS = 16
CONCURRENT_REQUESTS_PER_DOMAIN = 8
DOWNLOAD_DELAY = 0.25
RANDOMIZE_DOWNLOAD_DELAY = True
AUTOTHROTTLE_ENABLED = True
AUTOTHROTTLE_TARGET_CONCURRENCY = 4.0

AUTOTHROTTLE_ENABLED adjusts the delay from observed latency, which is the closest thing in any client here to reacting to the target instead of guessing at it. Worth turning on for anything unattended.

RANDOMIZE_DOWNLOAD_DELAY is on by default and multiplies the delay by a factor between 0.5 and 1.5. Leave it on.

Timeouts

DOWNLOAD_TIMEOUT = 30

One number, covering the whole download. Unusually, this one is a total, so Scrapy needs less wrapping than the plain clients do.

The other family

Not supported by the built-in middleware. Requires a third party downloader middleware or a local relay that speaks one scheme on the outside and the other on the inside.

Confirming it works

def parse(self, response):
    self.logger.info("came out through %s", response.text.strip())

pointed at an echo service, run once with the middleware enabled and once disabled. And log response.meta.get("proxy") on failures: when a rotation scheme misbehaves, the failing request naming its own value is the fastest way to see the pattern.
