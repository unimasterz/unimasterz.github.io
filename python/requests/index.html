requests: session scope, env override, and the https key trap

The most used client in this list, and the one with the most surprising precedence rules. Tested against requests 2.32 on Python 3.11.

Where the setting goes

Three scopes, and they behave differently.

import requests

# per call: explicit, never surprises anyone reading the code r = requests.get(url, proxies=P, timeout=(5, 20))

# per session: what most jobs want s = requests.Session() s.proxies = P r = s.get(url, timeout=(5, 20)) ```

The session version is what you want for anything that makes more than a handful of calls, because it also keeps the connection open between them.

Anything not using the session goes direct

A stray requests.get(...) anywhere in the file bypasses the session entirely. These hide in error handlers and in retry code, which is exactly where you least want a direct connection. Search the project for requests.get and requests.post before you trust a run.

The https key trap

The dict is keyed by the scheme of the site you are visiting. The value describes how you reach the hop. Those are different things, and both values are usually http://.

P = {
    "http":  "http://user:pass@198.51.100.14:8080",
    "https": "http://user:pass@198.51.100.14:8080",
}

Putting https:// in the second slot tells requests to speak TLS to the hop itself. Unless your provider explicitly offers that, the connection fails or hangs, and the error message points nowhere useful.

Environment variables beat your code

This is the part that costs people afternoons. If trust_env is left at its default, requests reads the environment and the environment wins over the session dict.

SourceBeats
per call proxies= argumenteverything
environment variablesthe session dict
session .proxies dictnothing above it

So a session you carefully configured is silently overridden by a variable somebody set in the shell profile, in a Dockerfile, or in a systemd unit two years ago.

To take the environment out of the picture:

s = requests.Session()
s.trust_env = False
s.proxies = P

To find out whether it is affecting you right now:

import os
print({k: v for k, v in os.environ.items() if "proxy" in k.lower()})

Both upper and lower case spellings are read. On most platforms the lower case form wins when both exist, which is a detail that matters when two different tools set two different values.

Who resolves the name

For the http scheme, your machine resolves the hostname and requests connects through the hop to the resulting address.

For the other family, the spelling decides:

pip install "requests[socks]"
ValueResolution
socks5://host:1080local
socks5h://host:1080at the far end

Most people who reach for this want the second and type the first. Confirm with probe two rather than trusting the documentation, including this page.

Credentials with awkward characters

An @ or : in a password breaks the url before requests ever sees it as credentials.

from urllib.parse import quote
p = quote(raw_password, safe="")
line = f"http://{quote(user, safe='')}:{p}@198.51.100.14:8080"

There is no separate argument for credentials in requests, so encoding is the only route.

Timeouts

A bare number sets both phases to the same value. A tuple sets them separately, which is what you want.

r = s.get(url, timeout=(5, 20))   # 5s to connect, 20s between chunks

Neither form bounds the total call. The read clock resets on every chunk, so a slow trickle holds the call open indefinitely. For anything unattended, add a ceiling above the library.

Retries at the right layer

Retrying with a loop around s.get re-runs your code. Mounting a retry policy handles it inside the connection pool, which is generally better behaved:

from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

r = Retry(total=4, backoff_factor=0.6, status_forcelist=[429, 500, 502, 503, 504], allowed_methods=["GET", "HEAD"]) s.mount("https://", HTTPAdapter(max_retries=r, pool_maxsize=20)) s.mount("http://", HTTPAdapter(max_retries=r, pool_maxsize=20)) ```

backoff_factor gives you growing gaps. It does not add randomness, so if many workers fail at the same moment they retry in unison. Add your own jitter if you run more than a few.

Note that pool_maxsize matters once you go parallel: the default is small, and threads beyond it queue for a connection rather than opening one.

Confirming it works

Two lines at startup, and a run that refuses to continue when it is wrong:

seen = s.get("https://api.ipify.org", timeout=15).text.strip()
print("requests is going out through:", seen)

Run it once with the session and once without. Two different answers means the setting applied.
